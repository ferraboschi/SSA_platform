## 1. [BLOCKER/perm-leak] Anonymous getCurrent() fallback returns roleKey 'manager', granting full manager capabilities with no session
- **src/lib/data/supabase/index.ts:736**  (auth-roles)
- Why: Confirmed real. At src/lib/data/supabase/index.ts:727-743, getCurrent() returns a synthetic anonymous user with roleKey:"manager" when there is no Supabase session. This datasource is the one active in production (provider.ts selects createSupabaseDataSource when USE_SEED=false + Supabase configured; .env.local has USE_SEED=false). Multiple server actions authorize solely on this roleKey: src/lib/share-links/actions.ts:20, src/lib/exam-links/actions.ts:36, src/lib/sync/actions.ts:22, src/lib/economics/actions.ts, src/lib/esami/actions.ts:20, src/lib/data/course-educator-actions.ts — all gate with `roleKey === "admin" || "manager"`. These are Next.js server actions (separate POST endpoints) and are NOT protected by the (app)/layout.tsx redirect("/login"), which only gates page/RSC rendering, not direct action invocations. Therefore an unauthenticated POST to one of these actions resolves getSession()→getCurrent()→synthetic manager, passes the role check, and gains full manager capabilities (mint share links, trigger Shopify/Airtable syncs, create exam links, read finance) with no session. The code's own comment admits this is a stopgap ("so SSR pages don't crash while we wire up auth"), but defaulting an unauthenticated principal to a privileged role rather than an unprivileged/denied one is a genuine privilege-escalation / auth-bypass.
- Fix: The anonymous fallback must never grant a privileged role. Either return null/throw from getCurrent() when there is no authUser and have getSession() propagate an unauthenticated session, or give the placeholder an unprivileged roleKey that maps to zero capabilities (e.g. a new "guest"/"none" role) so the `roleKey === "manager"` checks in the server actions deny access. Additionally, server actions should not rely solely on a synthesized roleKey — they should verify a real Supabase session (sb.auth.getUser()) before authorizing, since the layout redirect does not cover server-action POST endpoints.
